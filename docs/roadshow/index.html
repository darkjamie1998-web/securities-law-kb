01 · 业务场景

从业务问题出发，而不是从技术原理出发

把分散在法规、规章和交易所规则中的要求，转成一份可追溯的研究底稿，帮助业务人员更快找到依据、更清楚解释依据。

场景 01

为减持方案设计做规则研究

围绕股东身份、股份来源、减持方式和计划安排，快速汇集需要逐项核查的规则。

系统可以协助

  • 定位预披露、减持比例、时间区间和后续公告要求
  • 检索不得减持、窗口期及特殊主体适用规则
  • 沿关联关系追溯上位规则与交易所配套规定
形成：待核查事项清单 + 具体条号 + 原文依据 + 官方原文入口
场景 02

客户信息披露咨询

面对“是否需要披露、何时披露、谁来披露、能否暂缓或豁免”等问题，先找到规则，再讨论客户事实。

系统可以协助

  • 统一检索信息披露管理办法及交易所配套规则
  • 按法规、条号和业务关键词定位披露义务
  • 在当前法规范围内提问，减少跨主题干扰
形成：初步研究摘要 + 适用条文 + 需补充核实的客户事实
场景 03

解答客户问题时附上依据

不只给一句“AI 认为”，而是同时提供法规名称、具体条号和相关原文，方便内部审核和客户沟通。

系统可以协助

  • 先进行多轮法条检索，再组织中文研究回答
  • 点击引用核对库内原文，或继续打开官方原文
  • 库内未收录、条号未命中时明确标注，不隐藏缺口
形成：客户沟通草稿 + 法规名与条号 + 可复核的证据链
业务边界：系统辅助“查规则、读原文、做底稿”，不会自动出具可执行减持方案或正式合规意见。具体事项仍须结合主体身份、板块、股份来源、承诺、交易方式和最新监管规则复核。

03 · 可溯源回答

一条有依据的回答，是怎样形成的

AI 不替代法规库，而是在法规库之上做检索和组织；每个结论都应能回到证据。

1

提出业务问题

用自然语言描述客户事项，可选择全库或当前法规范围。

2

Agent 多轮检索

根据问题自主调整关键词，最多进行多轮模型与检索循环。

3

组织研究回答

基于检索到的条文归纳要求，找不到依据时明确提示。

4

附法规与条号

保留正文引用和完整参考列表，区分已命中与未收录。

5

打开证据核对

查看库内原文、阅读器定位及官方原文入口，再形成业务口径。

04 · 使用方式

既能独立使用，也能融入用户自己的 Agent 工作流

不是再增加一个“信息孤岛”，而是让证券法规能力出现在业务人员真正工作的地方。

方式 A · 现已具备

独立打开工作台

适合法规检索、专题研究、原文阅读，以及需要集中注意力的方案底稿整理。

  1. 启动本地面板，浏览器打开研究工作台
  2. 搜索法规或法条，进入连续阅读器
  3. 打开对话研究，围绕全库或当前法规提问
  4. 点击引用核对条文，必要时打开官方原文

便携分发：便携包内嵌 Python 运行时、依赖和知识库，目标机器无需另装 Python 或联网下载依赖。本地关键词检索与阅读可离线使用；AI 对话、Wiki 和每日同步仍需相应模型网关或官网网络。

方式 B · 标准 API 可接入

作为 Agent 能力接入 WorkMate / WorkBuddy

把知识库封装成用户原有助手可调用的专业工具。用户仍在原来的对话框里工作，由助手在需要时查询证券法规并带回依据。

  1. 在本机或内网启动知识库 HTTP 服务
  2. 按目标 harness 配置自定义 HTTP 工具、连接器或 Skill
  3. 用户直接提问，原有 Agent 调用检索或对话接口
  4. 将法规名、条号、原文和引用融入邮件、方案或研究底稿

不是替换用户的助手，而是给用户的助手增加“证券法规专业能力”。

05 · 更新与有效性

每日检查更新，让法规有效性可管理、可核对

不是笼统承诺“AI 知识永远最新”，而是用官方来源、增量同步、版本留存和状态提醒建立一套可检查的维护机制。

每日增量检查

通过 crawler.sync 检查已启用的官方公开栏目。可交给 WorkMate 定时任务或 Windows 调度器每日执行一次。

内容变更识别

根据正文哈希识别新增、变化和未变化；未变化跳过，变化时重建条文与中文分词索引。

旧版快照留存

法规内容变化时保留旧版及旧条文，默认检索优先展示当前版本，避免把历史与现行内容混在一起。

状态透明可追踪

同步日志记录新增、更新与失败；首页显示最近同步，数据超过 7 天会出现核对官方原文提醒。

运行前提：仓库提供同步命令和日志，但不内置自动调度器，需要在外部配置每日触发。当前快照的最近成功同步为 2026-09-22、最近内容更新为 2026-09-28；正式演示或分发前应先执行同步并检查日志。
官方来源与采集合规

当前数据以交易所公开栏目为主，并通过中国人大网、中国政府网等做定向补充。系统仅采集公开发布的法规文本；抓取客户端采用每站串行、默认至少 5 秒间隔与随机抖动、robots.txt 检查、指数退避、单来源上限和连续失败熔断。

覆盖范围可持续扩展，但不应理解为已经完整覆盖所有国家法规库、证监会栏目和全部交易所规则。具体业务仍需核对官方最新原文。

07 · 技术底座

技术隐藏在背后，业务看到的是可靠与易用

四层结构把官方文本、法条知识、研究服务和用户工作台连接起来。

第一层

官方公开来源

限频采集、原始留档、增量检查，持续沉淀法规文本。

第二层

法条级知识库

按条文组织内容，建立关键词索引、关联关系与版本快照。

第三层

检索与研究服务

精确检索、多轮对话、引用归一化、证据匹配和标准 API。

第四层

面板与 Agent

独立工作台直接使用，或由 WorkMate、WorkBuddy 等 harness 调用。

给技术同事：实现要点与当前配置
  • 服务与部署：Python 3.14、FastAPI、原生 HTML/CSS/JavaScript；SQLite 单文件数据库，WAL 支持服务与后台任务并发读写。
  • 检索：精确条号、jieba 中文分词 BM25、trigram FTS 与 LIKE 兜底；预留 API embedding + 向量 RRF 混合检索。
  • 当前模式：本机向量覆盖为 0，现场能力以中文关键词和精确条号检索为主；模型网关支持 embeddings 后可启用向量路。
  • 对话 Agent：OpenAI 兼容 API + tool calling，多轮调用 search_laws；前端展示 NDJSON 阶段事件，不是 token 级流式输出。
  • 引用：后端统一阿拉伯数字与中文条号，拆分多引用，返回 matched / 仅法规命中 / 库内未收录等完整状态。
  • 知识关联：LLM 辅助抽取法条关系，支持双向关联与图谱；关系覆盖度依赖库内法规覆盖，不作为权威规则关系证明。
  • 可靠性：LLM 硬超时、图谱实例锁与看门狗、SQLite backup API 备份、重复与空数据治理。
  • 接口：/api/search、/api/laws、/api/chat、/api/chat/stream、/api/laws/{id}/relations、/api/graph 等，可供 harness 进一步封装。

09 · 使用边界

让 AI 做研究助手，让专业人员做最终判断

使用时应保留的底线

  • 系统用于法规检索和辅助研究，不自动出具法律意见、合规意见或正式对客口径。
  • “现行有效”是库内状态标记，不等同于所有法规均已完成权威时效审查。
  • 减持、信息披露等具体事项必须结合客户事实、适用板块和最新监管要求复核。
  • AI 归纳可能存在遗漏或误读，引用与官方原文核对是形成业务结论前的必要步骤。

推荐的落地路径

  • 先用独立工作台承载高频法规查询与客户咨询研究。
  • 配置每日定时同步，持续检查核心主题覆盖与数据质量。
  • 将检索和对话 API 封装进用户已有 Agent，逐步融入实际工作流。
  • 围绕真实使用反馈补充规则来源、优化专题模板与审核流程。
